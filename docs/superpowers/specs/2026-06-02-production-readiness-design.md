# Spec Agent 正式上线改造设计

## 1. 背景与目标

当前项目已经完成主要业务能力重构，并具备本地账号密码登录、任务提交、实验管理、评测中心等基础功能。但现有登录模式仍属于单账号本地登录，权限边界仅为“已登录即可访问”，不满足正式上线场景下对多用户、角色隔离、资源归属、安全治理与运维治理的要求。

本设计用于明确正式上线前后的改造范围、优先级和阶段划分，避免后续围绕用户体系、权限控制和资源隔离出现返工。

本轮已确认的业务前提如下：

- 注册方式采用 `邀请码注册`
- 第一版角色模型采用 `管理员` / `普通用户`
- 第一阶段优先完成 `登录注册 + 用户角色权限`

## 2. 当前现状

### 2.1 认证现状

- 后端当前通过环境变量 `AUTH_USERNAME` / `AUTH_PASSWORD` 提供单账号登录
- Token 为项目自定义 Bearer Token，不依赖数据库用户体系
- 前端仅维护“是否已登录”状态，不具备角色态与用户态

### 2.2 权限现状

- 所有业务路由统一采用“登录即可访问”
- 没有角色权限依赖
- 前端没有按角色显示菜单、限制路由、限制页面动作的能力

### 2.3 数据归属现状

- 任务、文件、结果、实验采集、样本、评测等记录未保存资源归属字段
- 当前无法支持“仅本人可见”或“管理员可见全部”的对象级权限

### 2.4 线上风险现状

- 任务产物通过静态目录直接暴露
- 任务接口支持直接传入服务器本地路径
- CORS、接口文档、健康检查等线上暴露面较宽
- 默认密码、默认配置对正式环境不够安全

## 3. 设计原则

### 3.1 分阶段推进

本项目已接近上线，不适合一次性大重构。正式上线改造采用分阶段推进：

1. 先补用户体系与权限骨架
2. 再补对象级权限与资源隔离
3. 最后补安全、审计、运维收口

### 3.2 后端优先定义权限边界

前端菜单隐藏和路由控制只用于优化体验，真正的权限边界必须由后端控制。所有角色控制和对象级访问控制均以后端判定为准。

### 3.3 先铺基础字段，再逐步收口能力

第一阶段即使不全面启用对象级权限，也需要先为任务、文件、样本等核心资源补齐归属字段和审计字段，避免第二阶段返工。

### 3.4 保持与现有业务能力兼容

重构过程中优先保持现有谱图分析、实验管理、评测中心等业务链路可继续运行。正式上线改造应围绕用户体系与访问边界收口，不做与当前目标无关的大规模业务重构。

## 4. 总体阶段规划

### 4.1 P0 必须上线前完成

P0 目标是让系统具备最基本的多用户登录、角色控制和上线边界。

范围包括：

- 用户体系
- 邀请码注册
- 登录认证重构
- 管理员 / 普通用户两级角色
- 后端 RBAC 骨架
- 前端角色态、菜单与路由保护
- 核心资源归属字段铺底
- 服务端路径输入能力收口

### 4.2 P1 建议上线前完成

P1 目标是让系统从“能上线”提升到“多用户场景下更安全、更稳定”。

范围包括：

- 任务、文件、结果、样本、评测的对象级权限
- 任务产物下载鉴权
- 用户管理后台
- 邀请码管理后台
- 登录安全增强
- 生产环境接口暴露面收口
- 配置与密钥治理

### 4.3 P2 可上线后继续完善

P2 目标是增强运营能力、可审计能力和长期治理能力。

范围包括：

- 审计日志
- 更细粒度权限模型
- 账号找回与多因子认证
- 备份恢复、告警、仪表盘等运维增强

## 5. 第一阶段设计：登录注册与用户角色权限

### 5.1 目标

第一阶段目标如下：

- 支持管理员生成邀请码
- 支持用户使用邀请码注册
- 支持基于用户表的账号密码登录
- 支持管理员 / 普通用户两级角色
- 支持前后端统一识别当前用户角色
- 支持管理员专属页面和接口保护
- 为后续对象级权限准备资源归属字段

### 5.2 非目标

第一阶段暂不纳入以下内容：

- 全量对象级权限改造
- 全量产物下载鉴权替换
- 登录限流、验证码、多因子认证
- 全量审计日志
- 更复杂的角色或权限点系统

## 6. 核心模型设计

### 6.1 用户模型

新增用户集合，建议命名为 `users`。

字段如下：

- `user_id`：用户唯一标识
- `username`：登录名，唯一
- `password_hash`：密码哈希
- `role`：角色，取值为 `admin` / `user`
- `status`：状态，取值为 `active` / `disabled`
- `created_at`
- `updated_at`
- `last_login_at`
- `created_by`：若由管理员创建，可记录创建人

设计要求：

- `username` 唯一索引
- 禁止明文密码存储
- 第一版不要求邮箱、手机号等扩展资料

### 6.2 邀请码模型

新增邀请码集合，建议命名为 `invite_codes`。

字段如下：

- `invite_id`：邀请码记录唯一标识
- `invite_code`：邀请码字符串，唯一
- `role`：注册后赋予的角色，第一版可固定为 `user`
- `status`：状态，取值为 `active` / `disabled` / `expired` / `used_up`
- `expires_at`：过期时间
- `max_uses`：最大使用次数
- `used_count`：已使用次数
- `created_by`：创建邀请码的管理员 ID
- `created_at`
- `updated_at`

第一版建议：

- 邀请码允许配置有效期
- 邀请码允许配置使用次数，默认 `1`
- 普通邀请码默认只能注册普通用户

### 6.3 认证会话模型

当前自定义 Bearer Token 可继续保留一版，但其负载必须改为基于真实用户。

Token 载荷至少包含：

- `sub`：`user_id`
- `username`
- `role`
- `exp`
- `iat`

后端需要提供统一的当前用户解析能力，供接口依赖复用。

### 6.4 资源归属字段

第一阶段先在以下资源中补充 `created_by` 或 `owner_id`：

- 上传文件
- 分析任务
- 分析结果
- 实验数据采集批次
- 样本主档
- 评测批次

该字段的设计目标不是第一阶段全面启用，而是为第二阶段对象级权限打基础。

## 7. 权限模型设计

### 7.1 角色定义

第一版角色仅包含：

- `admin`：管理员
- `user`：普通用户

### 7.2 权限策略

采用“角色拦截 + 后续对象级扩展”的两层模型：

1. 第一阶段：
   - 管理员页面与接口由 `admin` 角色访问
   - 普通用户只允许访问普通分析和查看自身可见页面
2. 第二阶段：
   - 在角色基础上补对象级权限
   - 实现“普通用户只能查看自己的资源，管理员可查看全部”

### 7.3 第一阶段管理员专属能力

以下能力第一阶段必须收为管理员专属：

- 实验管理
- 数据采集
- 测评中心
- 用户管理
- 邀请码管理
- 样本删除
- 手动刷新统计

### 7.4 权限实现方式

后端增加统一依赖：

- `require_authenticated`
- `require_admin`
- `get_current_user`

其中：

- `get_current_user` 负责解析 Token 并返回统一用户上下文
- `require_authenticated` 只要求用户已登录且状态为 `active`
- `require_admin` 要求角色为 `admin`

前端增加：

- 用户态存储
- 角色态判断
- 路由守卫角色校验
- 菜单按角色显示

## 8. 接口设计

### 8.1 认证相关接口

第一阶段新增或改造以下接口：

- `POST /auth/register`
- `POST /auth/login`
- `POST /auth/logout`
- `GET /auth/me`
- `GET /auth/status`

职责说明：

- `register`：通过邀请码完成注册
- `login`：账号密码登录
- `logout`：前端登出与后端会话策略兼容
- `me`：返回当前用户信息，供前端初始化
- `status`：保留服务鉴权开关能力

### 8.2 管理员接口

第一阶段新增管理员接口：

- `GET /admin/users`
- `PATCH /admin/users/{user_id}/status`
- `POST /admin/users/{user_id}/reset-password`
- `GET /admin/invite-codes`
- `POST /admin/invite-codes`
- `PATCH /admin/invite-codes/{invite_id}/disable`

这些接口统一要求 `admin` 角色访问。

## 9. 前端设计

### 9.1 登录态升级为用户态

前端当前仅存储：

- 是否登录
- token
- username

第一阶段应扩展为：

- `userId`
- `username`
- `role`
- `status`
- `tokenType`
- `accessToken`
- `expiresAt`

### 9.2 页面与菜单权限

前端按角色显示菜单：

- `admin`：显示全部
- `user`：隐藏实验管理、数据采集、测评中心、用户管理、邀请码管理等管理员能力

同时增加路由级角色判断，避免普通用户通过手输地址进入管理员页面。

### 9.3 注册页

新增邀请码注册页，输入项至少包括：

- 邀请码
- 用户名
- 密码
- 确认密码

如邀请码无效、过期、用尽、被禁用，需要给出明确提示。

## 10. 资源访问与对象级权限预留

第一阶段暂不全面替换产物访问路径，但设计上必须预留第二阶段扩展：

- 任务、文件、结果、样本写入归属字段
- 所有服务层读取能力逐步具备按用户过滤的入口参数
- 后续下载接口改造时，能够复用当前用户上下文

第二阶段将重点替换以下能力：

- 任务列表按当前用户过滤
- 任务详情按归属校验
- 文件下载按归属校验
- 产物下载取消静态目录直出

## 11. 安全与配置要求

### 11.1 第一阶段最低要求

- 密码改为哈希存储
- 禁止继续使用单账号环境变量模式作为正式用户体系
- 生产环境必须配置强随机 `AUTH_SECRET`
- 默认密码不得用于生产环境

### 11.2 第二阶段收口项

- 登录失败限流
- 用户锁定策略
- CORS 白名单
- 关闭公开 `/docs` 与 `/openapi.json`
- 更严格的健康检查对外暴露策略

## 12. 迁移与兼容策略

### 12.1 登录兼容

现有本地单账号登录应视为临时模式。第一阶段切换后：

- 默认以用户集合登录为主
- 管理员首个账号可通过初始化脚本或种子逻辑创建
- 不再依赖 `AUTH_USERNAME` / `AUTH_PASSWORD` 作为长期正式方案

### 12.2 数据兼容

既有任务、文件、结果等历史数据可能没有归属字段。第一阶段应允许历史记录暂时为空，同时：

- 新创建数据必须写归属字段
- 第二阶段视需要提供数据回填脚本

## 13. 验收标准

第一阶段完成后，应满足以下标准：

- 管理员可生成邀请码
- 用户可通过邀请码完成注册
- 用户可使用用户名密码登录
- 前端可获取当前用户角色
- 普通用户看不到管理员菜单
- 普通用户访问管理员页面时被前端拦截
- 普通用户直接请求管理员接口时被后端拒绝
- 管理员可正常访问管理员专属能力
- 新上传文件、新建任务能够写入归属字段

## 14. 后续阶段概览

### 14.1 第二阶段

主题：对象级权限与资源访问收口

重点：

- 任务、文件、结果、样本按归属控制访问
- 产物下载接口化
- 输入路径白名单化

### 14.2 第三阶段

主题：安全、审计、运维治理

重点：

- 审计日志
- 登录限流
- 配置治理
- 暴露面收口
- 备份与告警

## 15. 推荐实施顺序

1. 用户模型与邀请码模型
2. 登录注册接口与当前用户接口
3. 管理员初始化方案
4. 后端角色依赖与接口保护
5. 前端登录态升级、注册页、权限菜单、路由守卫
6. 任务/文件归属字段写入
7. 第二阶段对象级权限改造

## 16. 结论

本设计采用“先用户体系与 RBAC、再对象级权限、后安全运维收口”的渐进式上线改造策略。这样既能优先交付邀请码注册、登录与用户角色权限，又不会为后续多用户隔离与安全收口埋下结构性返工风险。
